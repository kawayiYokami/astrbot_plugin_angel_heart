# AstrBot 事件流与私聊队列边界

## 功能目标

固定 AngelHeart 在 AstrBot 上的硬边界，避免把 PAI 的引导模型误搬过来。

## 触发时机

凡是讨论私聊忙碌处理、引导消息、并发应答、防抖实现时，都以本文边界为准。

## 核心流程

### 事件流

1. 任意消息到来都是一个事件
2. 消息历史由 AngelHeart 自建账本维护
3. 防抖账本可自管，但防抖等待只能挂在事件上
4. 防抖不是收集上下文后自行开跑，而是：
   - 旧事件 KILL
   - 只保留最后边界事件
   - 由该事件去请求
5. 决定激活时必须重建上下文

### 执行体

1. 每个被激活事件天然是一个独立子代理 / 远程应答委托
2. 多个边界事件分别激活后，天然可以并发
3. 这不是额外引入的“PAI 式并发委托”，而是 AstrBot 固有形态

### 私聊队列

1. 私聊无秘书
2. 私聊无离场 / 在场
3. 私聊无引导消息
4. 私聊忙碌时只能队列

根因：

```text
AstrBot 无法在已运行的子代理中注入消息
→ 后到私聊内容不能接入当前运行轮
→ 只能等当前轮结束，再由后续事件串行开新一轮
```

## 状态归属

- 私聊状态：空闲 / 忙碌（队列）
- 群聊状态：离场 / 在场 + 双防抖
- 防抖目的层与扣押实现层都属于群聊调度，不属于私聊

## 规则与计量

1. 可做：多事件分别激活后的天然并发子代理
2. 不可做：向已运行子代理注入新消息
3. 不可做：`targetDelegateId` 式引导已有委托继续当前轮
4. 不可做：观察器绕过事件激活自行开跑
5. 私聊忙碌只能队列，不是产品偏好

## 异常降级

1. 若误把“不能注入”写成“不能并发”，会错误禁掉 AstrBot 天然并发能力
2. 若把双防抖带进私聊，会违反私聊队列边界
3. 若激活时不重建上下文，会用陈旧快照请求

## 模块关系

```text
PAI / easy_call_ai 语义参考
→ AngelHeart 群聊双防抖状态机
→ AstrBot 事件=子代理 的执行边界
→ 私聊只能队列
```
