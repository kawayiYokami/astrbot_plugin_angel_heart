# AngelHeart - 智能群聊/私聊交互插件

[![License: AGPL v3](https://img.shields.io/badge/License-AGPL_v3-blue.svg)](https://www.gnu.org/licenses/agpl-3.0)
[![AstrBot Plugin](https://img.shields.io/badge/AstrBot-Plugin-blue)](https://github.com/Soulter/AstrBot)

AngelHeart 是一个专为 [AstrBot](https://github.com/Soulter/AstrBot) 平台设计的智能群聊/私聊交互插件。它采用**前台 / 秘书 / 助理**三角色协作与**两态群聊参与模型**，在需要时回复，在不该打扰时保持安静。

## ✨ 核心特性

### 🎭 三个角色

AngelHeart 不是“一个 AI 自己判断再自己说话”，而是三个各司其职的角色：

| 角色 | 职责 | 使用模型 |
|------|------|----------|
| **前台** | 整理消息、写入账本、调度入口 | 无（纯逻辑） |
| **秘书** | 巡检对话节奏、判断是否让助理接话 | 轻量模型 |
| **助理** | 实际生成回复内容 | 主模型 |

一条群聊消息的处理路径：

```text
收到消息 → 前台入账 → 秘书巡检 → 判断是否接话 → 助理生成回复
```

- **前台**不参与对话，只负责记账和调度。
- **秘书**用低成本模型做判断，快进快出；决定“不接话”就结束了，助理不会醒来。
- **助理**只在秘书放行后才生成高质量回复。

### 🎯 两态群聊参与模型

群聊只有“离场”和“在场”两种参与状态：

- **离场 (NOT_PRESENT)**：只记录消息，不主动加入聊天。只有被 @ 或命中点名词才会进场；若开启离场应答，复读或密集聊天可以得到一次回复，但回复后仍保持离场。
- **在场 (OBSERVATION)**：被点名时进入，在回复后继续保持。群聊暂时安静后，才由秘书判断是否需要接话；在场时间超过上限后，收到下一条消息时回到离场。

点名和普通群聊消息分别使用不同的等待规则；旧事件会被新的边界消息替换，避免针对半句话作答。

### 🔎 巡检：秘书的调度机制

秘书不是每条消息都去判断。它有自己的节奏——这就是**巡检**。

- **点名巡检**：有人 @ 助理或叫到助理时，前台会先等待一段补充消息时间，再交给秘书判断。
- **普通巡检**：助理已在参与群聊时，等群聊暂时安静下来，秘书才开始判断要不要接话。
- **边界替换**：等待期间的新消息会替换旧边界事件，只有最后一条消息能触发秘书判断。
- **同会话单飞**：同一群聊同时只允许一轮秘书判断在跑；上一轮还没结束时，新边界事件会重新等待。
- **秘书休息**：秘书决定不接话后，会先休息一段时间，期间普通消息不会立刻触发新巡检。
- **点名升级**：普通巡检等待期间有人叫到助理，当前巡检升级为点名巡检，不会创建第二套调度。

### ⚡ 能量：助理也会累

助理不是不知疲倦的。话说多了会累，**长发言比短发言更消耗精力**，所以长回复后的发言频率自然会降下来。

- 刚上线时精力充沛，聊什么都有劲。
- 说一次话会消耗一部分精力；发言越长，消耗越多。
- 累了就先歇着，等精力恢复一些，再由秘书判断要不要接话。
- 如果有人直接点名助理——就算累了也得回一句。

具体规则：

- 每次秘书普通巡检前，会按**经过的时间**自动恢复一点精力，不会超过上限。
- 精力够，秘书才进入判断；精力不够，保留巡检记录并重新计时，等恢复后再判断。
- **点名巡检**和**离场一次性应答**不受精力限制。
- 助理发出回复后，按实际内容消耗精力：

```text
消耗 = 基础消耗（默认 14） + 有效字符数 × 每字符消耗（默认 0.12）
```

短回复耗能少、恢复快，可以更频繁接话；长回复耗能多，说完需要更长时间恢复。扣到下限后不再继续扣，不会把助理卡死。

默认数值：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| 初始精力 / 上限 | 100 | 一开始精力充沛，恢复也不超过此值 |
| 精力下限 | -100 | 扣到底后不再继续扣 |
| 每秒恢复 | 0.6 | 大约 3 分钟从空恢复到满 |
| 回复基础消耗 | 14 | 每次开口的基础代价 |
| 每字符消耗 | 0.12 | 说得越多越累 |

精力按群独立保存在内存中，插件重启后回到初始值。`[能量设置]` 分组可调整全部参数；修改后新巡检立即生效，已有群的当前精力不重置。

### ⏰ 回复节奏管理
- **点名入场**：离场时只有明确点名会让助理进入群聊；可选的复读或密集聊天应答只回复一次，不会变成持续参与。
- **两类等待**：被点名时等待补充消息；在场时等群聊暂时安静后再由秘书判断是否接话。
- **避免连着插话**：助理回复后会休息一段时间；秘书决定不接话后也会休息，避免反复打断大家。
- **上下文感知**：每次真正分析前都按当前完整对话历史重建上下文。

### ⚡ 高效架构设计
- **轻量级前台缓存**：实时接收并缓存所有合规消息。
- **异步处理**：支持高并发场景下的稳定运行。
- **智能去重**：基于时间戳和内容的智能上下文合并。
- **私聊上下文接管**：现在私聊也会接管聊天记录重写与上下文构建，不再只覆盖群聊链路。

### 🔧 灵活配置
- **中心化配置管理**：通过 `ConfigManager` 统一管理所有配置项。
- **白名单机制**：精确控制插件生效范围。
- **自定义策略**：支持个性化回复策略指导。

### 🌟 群聊上下文管理
AngelHeart 提供了专为群聊场景优化的上下文管理功能，确保助理在群聊环境中能够准确理解对话上下文，提供高质量的交互体验。

### 💬 私聊上下文接管
除了群聊增强外，AngelHeart 现在也会接管私聊场景下的聊天记录重写与上下文构建：

- **私聊消息入账**：私聊消息会被纳入插件内部总账，参与后续上下文拼装。
- **直接响应兼容**：私聊仍保持主框架直接回复，不走秘书判定链路。
- **上下文连续性**：私聊请求发给助理前，也会使用 AngelHeart 的重写链路整理历史消息，保证上下文连续。

#### 原生 AstrBot 框架的限制
原生 AstrBot 框架在处理群聊上下文时存在以下问题：
1. **系统提示词注入问题**：原生的群聊上下文管理直接注入在系统提示词中，导致模型常常忽略这些上下文信息。
2. **上下文混淆**：原生的聊天记录会与原生群聊上下文管理功能产生混淆，造成信息冲突。
3. **私聊导向设计**：原生的聊天记录格式面向私聊场景，无法区分群聊中的不同发言人。
4. **用户指令统一问题**：模型将请求中的所有用户指令理解为来自同一个人，严重破坏了回答质量和准确性。

#### AngelHeart 的解决方案
AngelHeart 通过创新的上下文重构机制，完全解决了上述问题：
- **干净的上下文管理**：每次助理回复时，都能看到完全干净、明确的上下文管理，绝对不会发生发言人混淆。
- **格式化历史记录**：将完整对话历史重新格式化为单个 `prompt` 字符串，包含发言人身份、时间戳和内容。
- **动态决策注入**：将秘书决策策略精准注入到对话末尾，确保助理理解当前回复要求。
- **系统提示词隔离**：保持基础人格设定在独立位置，避免与动态上下文冲突。

## 🎯 主要功能

AngelHeart 让助理在群聊中变得更自然懂分寸：

- **智能回复时机**：秘书自动判断什么时候该说话，什么时候该闭嘴
- **自然融入群聊**：不是冷冰冰的机器人，而是会观察气氛的聊天伙伴
- **三角色协作**：前台整理消息，秘书快速判断，助理深度回复，省成本又高效
- **精力消耗机制**：长发言更累，短发言更轻，自动拉开接话频率
- **群聊上下文优化**：完美解决多人群聊中的发言人混淆问题
